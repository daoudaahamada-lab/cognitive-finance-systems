NARRATEUR : Bienvenue dans La Tour de l'Architecte, le podcast. Épisode 9 : le Poste de Contrôle. Deux histoires aujourd'hui autour de Claude Code, l'outil des équipes de développement, et de la différence entre guider et garantir. On pose la situation, tu réfléchis, et Nora, notre architecte, tranche.

NARRATEUR : Première histoire. Une équipe plateforme a un souci récurrent. Claude Code modifie régulièrement du code généré automatiquement, rangé dans un dossier réservé, et il lui arrive de toucher au fichier point env, celui qui contient la configuration sensible. Pourtant, le fichier CLAUDE.md du projet dit, en gras, que ces deux endroits sont interdits. Chaque semaine, l'équipe perd des heures à régénérer le code et à relire les modifications. Elle veut un blocage fiable, pour toute personne qui travaille dans le dépôt. Et quand une modification est bloquée, Claude doit recevoir une explication, pour changer d'approche.

NORA : La consigne est écrite, elle est en gras, et elle n'est pas respectée à chaque fois. Ce n'est pas un défaut de rédaction. CLAUDE.md, c'est du contexte. Ce n'est pas un contrôle.

NARRATEUR : Quatre idées, et il faut en retenir deux. Première idée : réécrire l'avertissement en majuscules, le remonter en haut du fichier, et le répéter dans chaque CLAUDE.md du dépôt. Deuxième idée : ajouter, dans les réglages partagés du projet, un hook Pre Tool Use sur les outils Edit et Write, qui s'arrête avec le code de sortie 2 et un message d'explication quand le chemin visé est protégé. Troisième idée : ajouter des règles deny sur le dossier de code généré et sur le fichier point env, dans le fichier de réglages commité avec le projet. Quatrième idée : déplacer ces consignes dans une skill dédiée. Mets sur pause si tu veux. Lesquelles tu gardes ?

NORA : La deuxième et la troisième. Le hook bloque l'action avant qu'elle s'exécute, et son message est renvoyé à Claude, qui peut alors s'y prendre autrement. La règle deny est simple et prioritaire : elle est évaluée avant toute règle allow, et elle s'applique à tous ceux qui utilisent le dépôt. Les deux se complètent. Écrire plus fort ne change pas la nature de CLAUDE.md, qui reste du contexte. Et une skill reste un ensemble d'instructions pour le modèle : elle n'empêche rien, et peut même ne pas être chargée au bon moment.

NARRATEUR : À retenir : quand l'énoncé dit malgré la consigne dans CLAUDE.md, la réponse est un contrôle déterministe. Un hook, ou une règle deny.

NARRATEUR : Deuxième histoire. Un éditeur de logiciels de paie lance chaque nuit, dans sa chaîne d'intégration continue, un traitement qui utilise Claude Code sans interface. Il trie les tests en échec sur une centaine de dépôts, et publie un résumé en JSON sur un tableau de bord. Problème : les résultats diffèrent d'une machine à l'autre. Certaines machines récupèrent des hooks laissés dans le dossier personnel d'un ancien développeur. Et plusieurs dépôts contiennent un fichier de configuration MCP qui branche des serveurs supplémentaires. L'équipe veut un comportement identique et reproductible partout, avec uniquement les outils nécessaires.

NORA : Sur chaque machine, Claude Code découvre automatiquement ce qui traîne autour de lui. Tant que cette découverte existe, deux machines ne feront jamais la même chose.

NARRATEUR : Trois pistes. Garder le mode sans interface, et ajouter au prompt une phrase qui demande à Claude d'ignorer les hooks et les serveurs MCP qu'il trouve. Lancer une session interactive sur chaque machine, et récupérer la sortie dans le journal du terminal. Ou passer en mode bypass permissions, pour qu'aucune demande d'autorisation ne bloque le traitement. À toi : tu fais quoi ?

NORA : Je lance Claude Code en mode headless, avec l'option bare. Elle saute la découverte automatique des hooks, des skills, des plugins, des serveurs MCP et de CLAUDE.md. Seule la configuration passée explicitement est utilisée. J'y ajoute l'option allowed tools, limitée aux outils dont le traitement a besoin, et une sortie au format JSON. Une phrase dans le prompt ne désactive rien : les hooks et les serveurs sont chargés par le client, avant que le modèle intervienne. Une session interactive n'est pas faite pour l'intégration continue : elle attend des validations. Et le mode bypass ne règle pas la variabilité, tout en augmentant fortement le risque. Il est réservé aux conteneurs ou aux machines virtuelles isolés.

NARRATEUR : À retenir : en intégration continue, pour un comportement identique partout, c'est le mode headless avec l'option bare, des outils explicites et une sortie JSON.

NARRATEUR : C'était l'épisode 9. Une idée traverse les deux histoires : une consigne oriente le modèle, seul un mécanisme garantit. Pour t'entraîner, c'est le neuvième étage de la Tour, face au Chaos Ops. Au prochain épisode : le Sommet, où tout se mélange, comme le jour de l'examen.
